# 006 · 工作计划：待办清单（to-do list）与完成日志（done log）机制

状态：完成
创建：2026-11-14

## 1. 目标

建立一套跨会话（session）不丢失的待办清单机制，供人和编程智能体（coding agent）共用：

- 之后要做的事，**先登记到待办清单再动手**。
- 复杂任务写工作计划（work plan，`design/NNN-plan_*.md`），待办条目只链接过去；不复杂的任务直接在条目下写几行简要计划，然后开工。
- 工作中发现的问题如果不属于当前分支（branch），不顺手修，先登记到清单靠后的待办池（backlog），保持分支专注。
- 完成或放弃的条目移出清单，写进单独的完成日志文件，清单本身保持短小。

## 2. 调研：网上的常见做法

## 3. 设计

### 3.1 文件

| 文件 | 内容 |
|---|---|
| `TODO.md` | 活动清单。三个小节，顺序固定：**进行中（Doing）**、**下一步（Next，按优先级排序）**、**待办池（Backlog，未排序）**。只含未完成条目 `- [ ]`。 |
| `DONE.md` | 完成日志。按月分组（`## YYYY-MM`），月份与条目都按时间倒序。条目为 `- [x]`（完成）或 `- [-]`（放弃）。 |

`STATUS.md` 的"下一步"一节改为指向 `TODO.md`，不再重复列出任务，避免两处不一致。`STATUS.md` 仍负责全局状态与时间点。

### 3.2 条目格式

`TODO.md`：

```
- [ ] **T-012** 标题 · 登记 2026-11-14 · 截止 2026-12-02 · 分支 `feat/x` · 计划 [006](design/006-plan_x.md) · 来源 T-010
  - 计划：1. …；2. …；3. …
  - 备注：…
```

- 必填：复选框、`**T-NNN**`、标题、`登记 YYYY-MM-DD`。
- 选填（`DONE.md` 中的 `计划` 同样只在有 design 计划时写）：`截止`（有硬期限时）、`前置`（依赖的条目）、`分支`（开工后）、`计划`（复杂任务，链接到 design 文献）、`来源`（在哪个条目的工作中发现的）。
- 不复杂的任务在子条目 `计划：` 中写简要步骤；复杂任务写 design 计划，条目只放链接，不复制内容。
- 判断"复杂"：改动多个模块、新增核心库能力或需要分环节审查的，写 design 计划（此标准写入 `AGENTS.md` 第二条）。研究的预注册（pre-registration）写在研究自己的 `README.md` 中，不因此单独写 design 计划。

`DONE.md`：

```
- [x] **T-012** 标题 · 完成 2026-11-20 · PR #5 · 计划 [006](design/006-plan_x.md) — 一句话结果
- [-] **T-013** 标题 · 放弃 2026-11-21 — 放弃原因
```

### 3.3 编号

- 新编号 = `TODO.md` 与 `DONE.md` 中出现过的最大编号 + 1，三位数字补零。编号永不复用。
- 分支上的 `TODO.md` 改动合并后才出现在 `main`，所以 `main` 上的"进行中"可能滞后。开工时尽早推送分支并开草稿 PR；开工或分配编号前先看未合并的分支与 PR（具体命令见 `AGENTS.md`）。
- 两个分支仍可能撞号：以先合入 `main` 的为准，后合入的改号，并同步修改 `来源` 与计划中的引用（测试会发现重复编号）。
- 所有改动都走功能分支（feature branch）与拉取请求（PR, Pull Request）、变基合并（rebase merge），不直接提交 `main`。只登记不开工时随当前分支提交，没有分支时开 `chore/todo-<内容>` 小分支。
- 放弃或暂停一个分支前，用一个小 PR 把它的条目落到 `main`：标 `[-]` 移入 `DONE.md`，或放回"下一步"/"待办池"并写明进度；分支上新登记的其他条目一并带过去。

### 3.4 流程

1. **登记**：任何要做的独立任务先写进 `TODO.md`（当前条目内部的小步骤写在它的子条目里，不另开编号）。当前工作的放"进行中"；排定的放"下一步"并按优先级插入；暂不排序的放"待办池"末尾；工作中发现、不属于当前分支的问题也放"待办池"末尾，并写明 `来源`。
2. **开工**：把条目移到"进行中"，填上 `分支`；复杂任务先写 design 计划并链接。
3. **完成**：在同一个分支（多 PR 任务则在最后一个 PR）里把条目从 `TODO.md` 删除，加到 `DONE.md` 当月小节（没有就在最上面新建），按日期倒序放置（变基冲突时按日期重排），写上完成日期、PR 编号和一句结果（先开 PR，拿到编号后补进条目再合并）。放弃同理，用 `[-]` 并写原因。
4. **整理（grooming）**：每次改 `TODO.md` 时顺手检查待办池：已失效的标为放弃移走；变得重要的提到"下一步"。

### 3.5 自动检查

新增 `tests/test_todo.py`，在 `python -m pytest` 中运行，只读这两个文件，不联网：

- 三个小节都在，顺序正确。
- 每个条目格式正确，有登记或完成/放弃日期，日期合法；`TODO.md` 的选填字段只能是已知的几种，`截止` 日期合法，`前置`/`来源` 引用的编号存在；`DONE.md` 的完成条目必须有 PR 编号和结果，放弃条目必须有原因。
- 看起来像条目却不合格式的行（缩进、别的项目符号、复选框写错、带粗体编号的行）一律报错，不静默跳过；代码块未闭合也报错。
- `TODO.md` 只有 `[ ]`，`DONE.md` 只有 `[x]` / `[-]`。
- 编号在两个文件之间不重复。
- `DONE.md` 的月份小节合法、不重复、倒序，条目日期落在所在月份内并倒序。
- 校验逻辑写成纯函数，测试同时检查真实文件和一组故意写错的样例。

## 4. 步骤

分两个环节（stage），每个环节结束做双闸审查（dual-gate review，见 `.claude/skills/dual-gate-review/SKILL.md`）。

1. **规则与文件**：本计划、`TODO.md`（把 `STATUS.md` 原"下一步"迁入）、`DONE.md`、`AGENTS.md` 规则、`STATUS.md` 与 `design/README.md` 更新、`README.md` 中英目录说明。
2. **格式检查测试**：`tests/test_todo.py`。

完成后推送分支、开 PR，拿到 PR 编号后把本任务（T-001）移入 `DONE.md`（写上 PR 编号）并提交，再以变基合并（rebase merge）保持 `main` 线性历史。

## 5. 验收标准

- 两个环节都通过双闸审查，没有遗留的严重问题。
- `python -m pytest` 通过，且故意写错的条目会让 `test_todo.py` 失败。
- `AGENTS.md` 写清楚登记、开工、完成、待办池四个动作，新会话的智能体只读 `AGENTS.md` 就知道怎么用。
